# Backend

The backend is a FastAPI application that serves authenticated meeting
action-item, meeting-insight, and media-transcription endpoints. It verifies
Supabase bearer tokens and uses a request-scoped Supabase client configured
with the caller's token. Meeting insights are generated by the Gemini-backed
provider in `app/services/ai/gemini.py`; uploaded audio/video is processed by
local Whisper and FFmpeg.

API requests use the Supabase anon key with the caller's bearer token. The
separate durable-processing worker uses the backend-only
`SUPABASE_SERVICE_ROLE_KEY` to claim jobs and access private media; it must
never be exposed to the frontend. See
[`../docs/architecture.md`](../docs/architecture.md) for request and data-flow
details.

## Prerequisites

- Python 3.12 is the documented development version; use a compatible Python
  version if required by the installed Whisper/PyTorch dependencies.
- Node.js and npm for the separate frontend.
- A configured Supabase project with the required migrations applied; see
  [`../database/README.md`](../database/README.md).
- A Gemini API key for meeting-insight generation.
- FFmpeg installed and available on `PATH` for audio extraction from uploaded
  audio/video. Whisper downloads its model when first used and runs locally;
  transcription can be slow on CPU.

The health endpoint can run without making Gemini or transcription requests,
but application startup loads the required backend settings.

## Configuration

Create `backend/.env` locally. The backend reads these settings through
`pydantic-settings`; environment variables can also provide the settings:

| Name | Required | Used for |
|---|---|---|
| `GEMINI_API_KEY` | Yes | Authenticates Gemini meeting-insight generation. |
| `GEMINI_MODEL` | No | Selects the Gemini model; defaults to `gemini-3.8-flash`. |
| `SUPABASE_URL` | Yes | Supabase project URL used by the backend client. |
| `SUPABASE_ANON_KEY` | Yes | Public/anon Supabase key used with the caller's bearer token. |
| `SUPABASE_SERVICE_ROLE_KEY` | Required by combined API/worker service | Privileged database and private-storage access for the durable worker started by the API lifespan. |
| `FRONTEND_ORIGIN` | No | Exact browser origin allowed by API CORS when configured; if unset, only the two localhost development origins are allowed. Do not include a path or trailing slash. |

Keep the service-role key server-side and configure it only in the Render web
service or local backend environment. Never expose it to frontend code or a
`NEXT_PUBLIC_` variable. Never commit `backend/.env` or paste secret values
into source code, documentation, or logs.

## Install and run

From the repository root in PowerShell:

```powershell
py -3.12 -m venv backend\.venv
.\backend\.venv\Scripts\Activate.ps1
python -m pip install -r backend\requirements.txt
```

If activation is unavailable, use the virtual environment's interpreter
directly. Start the API from the `backend` directory:

```powershell
cd backend
python -m uvicorn app.main:app --reload
```

The API listens at `http://127.0.0.1:8000`; its health endpoint is
`http://127.0.0.1:8000/health`, and interactive API documentation is at
`http://127.0.0.1:8000/docs`.

## Durable processing worker

Transcription and insight requests are persisted as jobs before the API returns
HTTP 202. FastAPI starts one supervised synchronous worker thread during its
lifespan and signals it to stop during shutdown. The worker runs outside the
ASGI event loop, and unexpected exits restart with a bounded delay. From the
`backend` directory, start the combined service with:

```sh
uvicorn app.main:app --host 0.0.0.0 --port $PORT --workers 1
```

Run exactly one Uvicorn worker process for this combined deployment; do not
pass `--workers` greater than one or start a separate `python -m app.worker`
process alongside the API. Configure `SUPABASE_SERVICE_ROLE_KEY` on the
backend service. The worker continues to claim jobs only through the database's
atomic claim function. A 120-second lease is renewed every 30 seconds. On
restart, pending/retryable jobs remain available, and jobs with expired leases
can be reclaimed. Shutdown waits up to 25 seconds for a current job; if the
host terminates processing sooner, lease expiry allows recovery. Processing is
limited to three job attempts;
retryable failures use exponential delay starting at 30 seconds, capped at
15 minutes, with up to 20% positive jitter. Gemini also has its own request
retry policy, so a failed Gemini job may make up to nine provider requests
across the three job attempts.

The Phase 11 workflow is defined by
`database/migrations/20261030000100_phase11_durable_processing_jobs.sql` and
the forward-only corrective migration
`database/migrations/20261031000100_phase11_claim_job_meeting_id_ambiguity.sql`.
The corrective migration resolves the claim RPC's ambiguous `meeting_id`
conflict target. Confirm the development database identity and migration state
before applying migrations; do not replay them blindly. The rollback-only
behavioral test is
`database/tests/verify_phase11_durable_processing_jobs.sql`; run it only in a
disposable development/test database with two existing test users, after
reviewing its prerequisites. In the local demo, live verification confirmed
that the worker claimed and processed a job, generated insights and action
items appeared on the dashboard, and completed results remained visible after
refresh. This reports the local demo path; it does not establish production
readiness or separate live crash-recovery verification.

## Tests

From the `backend` directory, run the existing tests with:

```powershell
python -m pytest -q
```

The tests use pytest and FastAPI's test client. Pytest is not listed in
`requirements.txt`; a fresh environment must have the test runner available
separately before this command can run. The tests use fakes for Supabase
interactions and do not verify live database RLS, RPC privileges, Gemini
availability, or transcription against real media.

## Processing limitations

Whisper inference and FFmpeg run in the worker thread on the API host; they
consume local compute and temporary disk space and can contend with API work.
Monitor service logs and queue health. The local demo verified a worker claim
and processing run. Live
crash-recovery, concurrency under failure, and other database projects require
their own verification.
